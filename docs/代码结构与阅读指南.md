# 代码结构与阅读指南

[返回首页](../README.md) · [项目概览](项目概览与技术栈.md) · [数据来源](数据来源与制作说明.md) · [运行原理](运行原理与接口说明.md)

## 1. 先认识目录

```text
项目根目录/
├─ README.md                 安装、配置、启动和文档入口
├─ .env.example              本机配置模板
├─ 启动项目.cmd              Windows 一键启动入口
├─ backend/
│  ├─ requirements.txt       Python 依赖
│  └─ app/
│     ├─ main.py             开发环境后端入口
│     ├─ production.py       同时提供网页和接口的入口
│     ├─ routers/            接收请求的接口模块
│     ├─ planning/           行程排程、交通核对和用餐匹配
│     └─ *_service.py        酒店、餐饮、天气等业务查询
├─ frontend/
│  ├─ package.json           前端依赖和启动、构建命令
│  ├─ vite.config.js         开发服务和代理配置
│  ├─ public/assets/         照片、地图图标和教程示例等资源
│  └─ src/
│     ├─ main.js             浏览器入口
│     ├─ App.vue             地图工作区与各功能的总装配
│     ├─ components/         页面、面板、表单和弹窗
│     ├─ composables/        各功能的状态和操作流程
│     ├─ map/                高德地图覆盖物和图层
│     ├─ planning/           前端表单、方案展示、保存和导出辅助逻辑
│     ├─ services/           HTTP 请求封装
│     ├─ tutorial/           教程步骤、演示场景和资料预加载
│     ├─ content/            页面介绍和资料来源说明
│     └─ styles/             公共样式与主题
├─ data/
│  ├─ formal/               正式运行数据
│  └─ schemas/              旅行请求与方案结果的 JSON Schema
├─ scripts/                 Windows 启动和本机配置读取脚本
└─ docs/                    项目说明
```

`components` 可以理解为“显示什么”，`composables` 负责“用户操作后发生什么、当前选中了什么”，`map` 负责“地图上怎样画”。前端 `planning` 主要整理输入和展示结果；核心行程计算在后端 `planning`。

## 2. 推荐的第一遍阅读顺序

1. [main.js](../frontend/src/main.js) → [CourseDemoEntry.vue](../frontend/src/components/CourseDemoEntry.vue)：先安装教程存储隔离，再检查高德配置，成功后加载工作区。
2. [App.vue](../frontend/src/App.vue)：看顶栏、侧栏、地图、信息面板与弹窗怎样组合，哪些状态在功能之间共享。
3. [tripForm.js](../frontend/src/planning/tripForm.js) → [useTripPlanning.js](../frontend/src/composables/useTripPlanning.js)：看表单怎样转换成请求，怎样提交、取消、切换方案和保存。
4. [routers/plans.py](../backend/app/routers/plans.py) → [route_orchestration.py](../backend/app/planning/route_orchestration.py)：看后端怎样接收条件并组织完整规划流程。
5. [service.py](../backend/app/planning/service.py)、[schedule.py](../backend/app/planning/schedule.py)：继续看景点筛选、顺序、时间和费用的计算。
6. [useTravelMap.js](../frontend/src/composables/useTravelMap.js) → [planMapLayer.js](../frontend/src/map/planMapLayer.js)：看结果怎样画成当前日路线，以及点击路线后怎样展示交通详情。

第一次阅读时可以先跟随一次“生成轻松方案”的调用过程，再单独研究住宿、餐饮和导出。

## 4. 后端如何分工

下表路径均位于 `backend/app/`。

| 模块 | 职责 |
|---|---|
| [main.py](../backend/app/main.py)、[production.py](../backend/app/production.py) | 注册接口、异常处理与应用生命周期；后者另提供前端构建资源 |
| [settings.py](../backend/app/settings.py) | 读取根目录 `.env`，集中管理服务配置、查询预算和缓存参数 |
| `routers/` | 接收 HTTP 请求，解析参数，调用对应业务模块并返回结果 |
| [trip_validation.py](../backend/app/trip_validation.py) | 按 Schema 和业务规则检查日期、时间、人数、偏好和景点编号 |
| [data_store.py](../backend/app/data_store.py)、[duck_content_store.py](../backend/app/duck_content_store.py) | 读取并缓存正式 JSON 资料 |
| [amap_client.py](../backend/app/amap_client.py) | 查询高德并转换为项目使用的地点、酒店、路径等字段 |
| [amap_transport.py](../backend/app/amap_transport.py) | 共用网络连接、并发控制、相同请求共享、缓存、期限与取消处理 |
| `transit_routes.py`、`driving_routes.py`、`path_routes.py` | 将服务商路径转换为统一交通详情和经纬度折线 |
| `hotel_service.py`、`dining_service.py`、`duck_restaurant_service.py` | 独立酒店和餐饮查询，整理候选与分类 |
| [weather_service.py](../backend/app/weather_service.py) | 查询、整理和缓存南京天气预报 |
| [api_models.py](../backend/app/api_models.py)、[errors.py](../backend/app/errors.py) | 接口模型与统一错误响应 |

接口按主题放在 `routers/system.py`、`attractions.py`、`map_services.py`、`plans.py`、`plan_trace.py`、`duck_culture.py`、`duck_restaurants.py` 中，完整入口见 [接口说明](运行原理与接口说明.md)。交通预留分钟数由`backend/app/travel_time_rules.py`统一计算，初排、实际路径与过程窗口共用同一规则。

## 5. 规划模块建议分层阅读

以下文件均位于 `backend/app/planning/`，按“先生成、再核对、再匹配用餐区”的顺序理解。

| 层次 | 文件 | 业务作用 |
|---|---|---|
| 总流程 | `route_orchestration.py` | 组织初步规划、实际交通、时间核对、局部调整和最终结果校验 |
| 初步排程 | `service.py`、`schedule.py`、`day_schedule.py` | 筛选景点、安排每日顺序、时隙与费用 |
| 首末景点与距离复核 | `priority_visit.py`、`last_stop.py`、`day_distance_review.py` | 优先景点下午预留、末站返程评分、查询高德前超过8公里的单日重排与当天排序 |
| 规则与顺序 | `rules.py`、`time_rules.py`、`route_order.py`、`day_repair.py`、`nearby_attractions.py` | 偏好评分、开放规则、邻近关系与有限顺序调整 |
| 交通核对 | `transport.py`、`transit_enrichment.py`、`route_schedule.py` | 先估算连接成本，再用实际交通信息核对每天是否可行 |
| 调整与补排 | `route_schedule.py`、`route_repair.py`、`dinner_recovery.py` | 记录实际交通造成的空档、尝试未安排景点补排并处理晚餐返程冲突 |
| 过程记录 | `trace.py` | 记录实际候选评分、选择、优化、交通及餐饮事件，供流式接口发送 |
| 餐次预留 | `meals.py`、`visit_meals.py` | 为午餐、晚餐预留 60 分钟，处理长时间游览中的用餐选择 |
| 沿途区域匹配 | `route_meals.py`、`hex_matching.py` | 从正式快照取蜂巢，判断路径相交并选择可安排的用餐区域 |
| 输出约束 | `plan_contract.py`、`notices.py`、`models.py` | 检查结果关系，管理提示原因、规划状态和异常 |

## 6. 修改时应该同步查看什么

更改接口字段时，先查看 [旅行请求 Schema](../data/schemas/trip_request.schema.json) 和 [方案结果 Schema](../data/schemas/plan_response.schema.json)，再检查前端组装、结果读取、保存与导入逻辑。餐次的当前结果位置是 `plans[].days[].legs[].meals`，地图与两条时间轴都会使用它。

更改地图显示时，从对应图层和其调用方一起阅读：图层维护高德覆盖物，状态模块决定何时显示、选择或清理。更改正式数据时，应核对景点编号、图片映射、餐饮成员引用与数据版本之间的关系，详见 [数据说明](数据来源与制作说明.md)。

前端现有命令为 `dev`、`build`、`preview`。日常运行、构建与同源预览的完整操作见 [首页](../README.md)；功能验证可沿 [运行原理文档的开发者工具观察流程](运行原理与接口说明.md#6-用浏览器开发者工具观察一次完整流程) 检查实际输入、请求与显示结果。
