# 运行原理与接口说明

[返回首页](../README.md) · [项目概览](项目概览与技术栈.md) · [代码结构](代码结构与阅读指南.md) · [数据来源](数据来源与制作说明.md)

## 1. 启动后发生什么

开发环境中，浏览器打开 Vite 提供的前端页面；`/api` 与 `/_AMapService` 请求通过开发代理转发到 FastAPI。构建后的同源运行方式由 `backend.app.production:app` 同时提供网页、接口和高德安全代理。两种启动命令见 [首页](../README.md)。

课设版的浏览器入口是 [main.js](../frontend/src/main.js)，首先加载 [CourseDemoEntry.vue](../frontend/src/components/CourseDemoEntry.vue)，调用 `GET /api/map/config` 检查三项高德配置。通过后才加载 `App.vue` 中的地图工作区；配置或连接有问题时显示提示和重试入口。

后端读取根目录 `.env`。浏览器取得高德 JS API Key 和安全代理地址，高德安全密钥、Web 服务 Key 与天气 Key 由后端读取。SDK 安全代理在转发时补充安全参数。配置“已填写”与服务商“实际接受该配置”分别在配置检查和真实查询中确认。

进入工作区后，各功能模块加载相应资料。底图和地图交互使用高德 JS API；正式景点、地铁、文化、餐饮快照为项目资料；酒店、搜索、交通和天气在对应操作中查询或复用缓存。

## 2. 从表单到行程的完整过程

### 2.1 收集旅行条件

用户先确认住宿和首末日起终点，再通过问卷或完整表单填写条件。两种填写方式共用 [tripForm.js](../frontend/src/planning/tripForm.js)；住宿选择先保留在草稿中，最终确认后写入旅行条件。

新规划默认次日出发、成人一人、无景点或标签预选，人数至少包含一名成人或学生。问卷第二题统一设置天数和每日时间；汇总的行程天数包含日期范围，出发日期单独对应第三题。问卷按进入汇总的来源区分正常填写、单题修改和缺失必选题补填，完整表单适合集中查看全部条件。“修改方案”恢复当前方案的条件快照，“重新规划”建立一份初始条件并保留住宿。

`buildTripRequest` 将界面选项转为 TripRequest 请求，主要内容如下。准确类型、枚举与必填规则见 [trip_request.schema.json](../data/schemas/trip_request.schema.json)。

| 字段 | 业务含义 |
|---|---|
| `request_id` | 本次旅行条件的标识 |
| `trip_days` | 各天日期、开始和结束时间 |
| `lodging`、`first_day_start`、`last_day_end` | 住宿位置、首日出发点和末日结束点 |
| `party`、`ticket_budget` | 成人、学生、儿童人数及门票预算 |
| `transport_preference` | 交通倾向 |
| `preferences` | 必去、不去、感兴趣的景点和主题偏好 |
| `allow_skip_meal_for_long_visit` | 用户对长时间游览中跳过一次用餐的选择 |
| `manual_locks` | v1 请求约定的空数组 |

### 2.2 提交并校验

[useTripPlanning.js](../frontend/src/composables/useTripPlanning.js) 保存条件快照，调用`POST /api/plans/trace?plan_type=relaxed&detail=full`，后台默认保存完整记录和实际进度。`plan_type`可为`relaxed`、`compact`、`duck`，每次生成一种；其他类型按需使用原始条件请求，再合并已取得的方案。收到逐行流中的`result`才显示成功；原`/api/plans`JSON接口仍可用。

[routers/plan_trace.py](../backend/app/routers/plan_trace.py)和原JSON入口共用[trip_validation.py](../backend/app/trip_validation.py)，检查字段格式、日期、时间、编号和偏好，条件错误返回422。生成后的流包含真实事件、最终结果或错误，取消连接会取消对应任务。

### 2.3 生成初步景点顺序

[route_orchestration.py](../backend/app/planning/route_orchestration.py) 中的 `generate_route_hex_plans` 组织完整过程。首先由 `service.py`、`schedule.py` 等模块结合开放时段、票价、偏好、游玩时长和点位距离安排景点。

轻松与鸭子采用建议时长，紧凑采用最短合理时长。每轮先核对开放、预算、完整用餐及返程。必去／兴趣编号去重后，每天按剩余数量除以剩余日期向上取整计算加分目标；首个必去10000／兴趣600，后续未达标200，达标后仅偏好项归零；下午预留提前计数。必去最后可行日和旅行末日保留优先，邻近景点仍可同日安排。标签120分、推荐、等级和邻近继续参与，距离每公里扣6分。`priority_scoring.py`计算分日规则，`schedule.py`分别使用数量目标和用餐时间，防止午餐后错误恢复200分。

一天初排结束后，[last_stop.py](../backend/app/planning/last_stop.py) 回到最后一个景点的选定轮次，把到当天终点的返程距离也计入比较。若必去／兴趣景点排在第一位且距离扣分超过50分或需要等待，[priority_visit.py](../backend/app/planning/priority_visit.py) 先为它保留当天较晚的可行时段，再尝试安排此前的景点。

多日方案的整体调整包含相近景点跨天一对一交换和同日顺序优化。随后，[day_distance_review.py](../backend/app/planning/day_distance_review.py) 检查出发点到首景点、相邻景点、末景点到当天终点的直线距离；超过8公里的日期最多单独重排一次，再优化该日顺序，之后进入高德查询。必去、费用、开放时间和完整餐次在试排时一起检查。这是一套有约束的启发式规划流程，结果给出实际安排和未安排原因。

### 2.4 使用实际交通核对和调整

后端向高德查询相邻节点的步行、公交或驾车路径，把返回的实际耗时和轨迹转换成项目统一结构，再核对当天时间是否仍可行。

交通耗时由[travel_time_rules.py](../backend/app/travel_time_rules.py)统一四舍五入到10分钟后再加10分钟余量，例如23分钟预留30分钟、26分钟预留40分钟；零耗时和不足5分钟的短步行预留0。当公交不可用、耗时超过90分钟或累计步行超过40分钟等条件触发时，查询同向出租车作为候选。交通核对造成空档时，从尚未安排的景点中尝试补入受影响日期；新连接核对后才采用。路径仍未取得的路段保留估算并给出提示。

高德传输层共用连接、限制并发，合并相同进行中的查询并缓存合法成功结果。规划还设有总体查询与时间预算；浏览器取消规划或断开时，接口取消对应任务并回收资源。预算参数集中在 [settings.py](../backend/app/settings.py) 和规划编排模块。

### 2.5 匹配沿途餐饮区域

每餐预留60分钟，午餐最迟14:00结束。[hex_matching.py](../backend/app/planning/hex_matching.py) 判断路径与蜂巢的空间关系，[route_meals.py](../backend/app/planning/route_meals.py) 结合用餐时间和快照中的候选信息分配区域。步行和道路段可按沿途相交关系筛选；公交乘车段结合可下车站点与步行部分筛选。

鸭子方案优先分日安排南京鸭正餐，再比较区域内正餐候选数量。当前 1～5 天旅行的鸭餐目标分别为 1、1、2、3、3 次，实际安排还受路线与时间可行性约束。餐次与区域写入对应交通段的 `meals`，随后按结果 Schema 与关系规则检查完整性。

## 3. 结果怎样驱动地图和时间轴

完整字段定义见 [plan_response.schema.json](../data/schemas/plan_response.schema.json)。可以先按下面的层次阅读：

```text
PlanResponse
├─ request_id / generated_at / data_version
├─ global_warnings                      整体提示
└─ plans[]                              已生成的方案
   ├─ plan_type                         方案类型
   └─ days[]                            每天的安排
      ├─ items[]                        景点、住宿和起终点节点
      └─ legs[]                         相邻节点间的交通段
         ├─ from_item_id / to_item_id    连接的节点
         ├─ mode / duration_minutes_rounded
         ├─ path_details                轨迹、分段和站点
         └─ meals[]                     沿该段安排的餐次与用餐区域
```

`items` 说明“去哪里、何时游览”，`legs` 说明“怎样从上一站到下一站”，`meals` 说明“何时在哪个区域用餐”。交通 `path_details.route_segments` 包含按步行、公交等方式分段的经纬度路径。

前端方案状态由 `useTripPlanning.js` 管理。选择方案或日期后，`PlanResults.vue` 显示方案信息，`PlanDayTimeline.vue` 和 `RouteTimeline.vue` 派生时间顺序，`useTravelMap.js` 将当前日数据交给 `planMapLayer.js` 绘制。餐饮区域交给 `diningMapLayers.js`，格内门店通过快照索引取得。地图与时间轴共用当前方案、日期和选择状态，因此点击节点或切换日期时可以同步变化。

## 4. 主要接口

运行后可在 <http://127.0.0.1:8000/docs> 查看 FastAPI 自动生成的接口文档、参数和响应模型。下表列出常用入口；端口随本机配置调整。

| 方法与路径 | 用途 | 主要实现 |
|---|---|---|
| `GET /api/health` | 后端健康状态 | `routers/system.py` |
| `GET /api/map/config` | 地图配置与课设版入口检查 | `routers/system.py` |
| `GET /api/attractions`、`/api/attractions/{attraction_id}` | 正式景点列表与详情 | `routers/attractions.py` |
| `GET /api/poi/search` | 按关键词、类别和可选中心搜索地点 | `routers/map_services.py` |
| `GET /api/hotels/search` | 指定中心附近的酒店候选 | 同上，调用 `hotel_service.py` |
| `GET /api/restaurants/search` | 主动查询附近餐馆 | 同上，调用 `dining_service.py` |
| `GET /api/duck-restaurants/search` | 独立在线鸭店检索 | `routers/duck_restaurants.py` |
| `GET /api/metro-network` | 返回正式地铁资料 | `routers/map_services.py` |
| `POST /api/travel-time` | 查询指定起终点及方式的交通路径 | 同上，调用 `amap_client.py` |
| `GET /api/weather` | 南京未来 10 天预报 | 同上，调用 `weather_service.py` |
| `GET /api/duck-culture`、`/api/duck-culture/{content_id}` | 文化文章列表与详情 | `routers/duck_culture.py` |
| `POST /api/plans?plan_type=…` | 生成指定类型的旅行方案 | `routers/plans.py` |
| `POST /api/plans/trace?plan_type=…` | 生成方案并逐步返回评分、调整、交通和餐饮记录 | `routers/plan_trace.py` |
| `GET/POST /_AMapService/{service_path}` | 高德 JS API 安全代理 | `routers/map_services.py` |

`map_services.py` 还提供 `GET /api/dining-density` 和 `GET /api/dining-areas/evaluate`，用于按给定中心在线查询餐饮采样与便利区域。当前普通分布、南京鸭专题和行程蜂巢使用正式快照；快照由前端动态导入，查看这些图层时可以在 Network 中观察相应静态资源加载。

业务错误统一返回 `error` 对象，包含 `code`、`message`、`retryable`、`details`。常见状态包括：422 输入不符合规则，502 外部查询失败，503 服务配置缺失，504 规划超时。页面根据错误内容提示重试或修改条件。

## 5. 保存、导出与教程

**本机保存**：旅行表单写入 `nanjing-webgis-trip-form-v1`，手动保存的方案集合写入 `nanjing-webgis-saved-plans-v2`。这些是当前浏览器 localStorage 中的键，记录包含原请求、已生成结果、方案类型和查看日期。打开记录时恢复保存的快照；本次历史放在页面内存中，同条件同类型重新生成更新原条目为最新结果，更改条件或类型则另存历史。刷新后可从手动保存重新打开方案。

**JSON 文件**：由 `itineraryJsonExport.js` 和 `itineraryFileImport.js` 处理，文件格式标识为 `nanjing-webgis-plan`、版本 1。文件包含原条件和已加载的方案，可导入其他浏览器或电脑。导入时检查结构与完整性，恢复当时的交通和用餐结果。

**PNG 行程单**：`itineraryExport.js` 构造行程单数据，`ItineraryExportSheet.vue` 渲染，`useItineraryExport.js` 使用 html-to-image 转为图片，提供预览和下载。天气在导出时取快照。

**使用教程**：23 步指引由 `tutorialSteps.js` 定义，场景由 `tutorialScenes.js` 组织。教程通过 iframe 复用实际应用，以临时存储隔离演示操作，准备完成的资料会在当前页面复用。可从 `HelpTutorial.vue` 与 `tutorial/demoContext.js` 跟进实现。

## 6. 用浏览器开发者工具观察一次完整流程

先按首页启动服务并进入页面，按 `F12` 打开开发者工具。下面的操作适合初次理解项目，也可作为修改后的人工核对流程。

1. **观察启动**：在 Network 面板清空列表后刷新，选择 Fetch/XHR，查看 `/api/map/config`、景点等请求。在响应中确认配置检查和资料返回，再查看地图相关外部资源。配置项以自己的 `.env` 为准。
2. **观察搜索**：搜索“鸡鸣寺”，筛选 `poi/search`，在参数中查看关键词与类别；比较响应结果、地图标记和收录景点详情。对应代码为 `services/api.js`、`useMapQueries.js` 与 `search/searchResults.js`。
3. **观察生成**：完成条件后生成轻松方案，打开`plans/trace?plan_type=relaxed&detail=full`，Payload看日期、位置、人数和偏好；逐行Response中的`result.response.plans[0].days`包含`items`、`legs`和`meals`。对应阅读`useTripPlanning.js`、`routers/plan_trace.py`和`generate_route_hex_plans`。
4. **观察联动**：切换日期并点击路段，对照响应中的节点编号、交通方式与路径，检查地图和两条时间轴是否对应当前日。再生成鸭子方案，查看 `plan_type=duck` 请求及鸭餐区域。
5. **观察静态餐饮**：开启餐饮分布、南京鸭分布或南京鸭门店，点击蜂巢与门店。结合 `diningSnapshotData.js` 和快照中的编号查看名单来源；资料首次加载后，重复开关可复用已取得的数据。
6. **观察保存**：手动保存方案，在 Application → Local Storage → 当前页面地址下查看上述两个键；刷新后打开保存记录。再导出 JSON 并重新导入，检查方案与当前日恢复情况。
7. **观察导出**：预览并下载 PNG，比较图片中的日期、景点、用餐和交通顺序。Console 中检查是否出现未处理异常。
8. **观察逐轮排程**：先正常生成，记录从开始就在后台保存；双击进度卡片，或在非输入状态双击反引号键，手动展开并查看此前全部步骤。收起后再生成不自动展开；左下角“展开排程调试面板”可重开。已展开时双击反引号隐藏面板和按钮，后台记录继续。窗口展示真实评分、试排、顺序、交通与餐饮，可筛选“采用调整”；`trace.py`负责记录，`usePlanningDebug.js`仅管理显示，`PlanningTraceWindow.vue`负责查看及回放。

开发者工具中能看到浏览器发送和收到的请求。后端向高德查询的过程应结合后端代码与运行窗口日志阅读；浏览器里的 `/api/plans` 是整个规划的入口。

## 7. 常见运行问题如何定位

| 现象 | 优先检查 |
|---|---|
| 停在配置检查页 | 后端是否启动，`/api/map/config` 是否成功，三项高德配置是否填写，修改后是否重启 |
| 进入页面但底图或服务报错 | 高德 Key 类型、对应安全密钥、来源限制、服务权限、额度和网络；在 Network 查看失败请求 |
| 天气不可用 | 和风天气 Host、Key、每日预报权限与后端返回的错误；天气为独立查询功能 |
| 酒店或交通查询失败 | 对应接口的错误响应、后端日志、外部服务网络和配额，再使用页面重试入口 |
| 更换浏览器后找不到方案 | 当前浏览器的本机记录独立存放，可从原浏览器导出 JSON，再到新浏览器导入 |
| 修改正式 JSON 后显示异常 | UTF-8 编码、编号引用、坐标顺序、版本和读取校验；后端正式资料有进程缓存，修改后重启并刷新 |

定位时先确定失败的请求、返回内容和对应模块，再判断是输入、配置、网络还是数据问题。代码入口可按 [阅读指南](代码结构与阅读指南.md) 的功能表查找。
