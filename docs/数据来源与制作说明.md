## 1. 先分清资料来自哪里

本项目把预先整理的资料保存为正式 JSON，把用户使用时需要更新的查询交给在线服务。地图底图由高德提供，景点、餐饮和行程等专题内容由项目叠加绘制。

| 内容 | 来源和取得方式 | 本仓库中的位置 |
|---|---|---|
| 40 个景点 | 景区、政府等公开资料整理，预先采集高德坐标并核对主入口 | [attractions.json](../data/formal/attractions.json) |
| 40 个景点照片映射 | 按景点编号记录本地照片、原网页与来源单位 | [attraction_images.json](../data/formal/attraction_images.json)、[景点图片目录](../frontend/public/assets/attractions/) |
| 8 条地铁线路、175 个站点 | 南京地铁公开资料核对范围，高德线路采集形成坐标与路径 | [metro_network.json](../data/formal/metro_network.json) |
| 餐饮分布与门店 | 高德地点服务预先采集、分类和人工复核后形成静态快照 | [dining_map_snapshot.json](../data/formal/dining_map_snapshot.json) |
| 8 篇鸭文化文章 | 地方志、政府、新闻等公开资料整理，正文附引用 | [duck_culture.json](../data/formal/duck_culture.json) |
| 六个推荐住宿片区 | 项目预设的参考坐标、范围和适合游客 | [accommodationOptions.js](../frontend/src/planning/accommodationOptions.js) |
| 底图、地点、酒店、交通 | 使用对应功能时查询高德地图 JS API 或 Web 服务 | [地图模块](../frontend/src/map/)、[amap_client.py](../backend/app/amap_client.py) |
| 南京天气 | 使用时查询和风天气未来 10 天预报，成功结果缓存 1 小时 | [weather_service.py](../backend/app/weather_service.py) |

本页介绍正式数据的制作方法；可直接运行的资料就是 `data/formal/` 下的五份 JSON。来源与日期应以各文件中的记录为准，页面的资料来源入口由 [dataSources.js](../frontend/src/content/dataSources.js) 提供。

## 2. 景点资料、坐标与图片

景点制作过程是“人工收集表 → 字段规范化 → 主入口坐标核对 → 正式 JSON”。收集内容包括名称、行政区、类别、标签、开放时段、闭馆规则、游玩时长、参考票价、预约渠道、推荐级别与资料来源。

主项目的数据制作过程使用工作簿维护资料，再结合字段映射、开放规则和坐标选择生成正式文件。本仓库运行时直接读取生成结果：每个景点的稳定编号 `id` 用来连接资料、照片、地图标记、偏好选择和规划结果。编号属于身份标识，例如当前有 `attr_041`，应按文件中的实际编号关联。

景点坐标为 GCJ-02，主要选择游客实际到达的主入口。它参与地图标记、住宿邻近关系和交通规划。直接使用景区几何中心，可能使交通路径落到不适合入园的位置，因此需要结合入口候选核对。

在 `attractions.json` 中，可重点查看 `opening`、`duration`、`ticket`、`reservation`、`location` 和 `sources`；来源条目含网页地址与核验日期。照片通过 `attraction_id` 对应景点，图片映射中的 `image_path` 指向前端资源，`source_url` 和 `source_organization` 说明出处。地图专属图标作为独立视觉资源，由标记模块按景点编号选用。

## 3. 地铁与文化资料

地铁专题根据南京地铁公开资料确定展示范围，预先保存 1、2、3、4、5、7、10、S1 号线的折线和站点坐标，并标注换乘、交通门户和邻近景点等主要站点原因。当前正式文件记录的核验日期为 2026-09-09。前端通过 [metroMapLayer.js](../frontend/src/map/metroMapLayer.js) 绘制线路和站点；行程中的公交换乘路径另由高德交通接口查询。

鸭文化文件保存 8 篇文章，正文中的引用编号对应各文章 `sources` 中的标题、链接和核验日期。后端提供文章列表与详情，前端文化面板和小鸭向导复用这些内容。

## 4. 餐饮采样点怎样确定

餐饮专题使用同一套固定六边形几何，共 461 格。采样围绕景点旅游活动范围展开，覆盖六条旅游走廊：

1. 钟山—主城—玄武湖—城北。
2. 老城—河西—鱼嘴—城南。
3. 城北—浦口沿江。
4. 钟山—阳山碑材—汤山。
5. 钟山—栖霞山—欢乐谷。
6. 老城南—雨花台—牛首山。

采样时将走廊折线转为局部平面距离计算，保留中心点距任一走廊不超过 2000 米的蜂巢。网格采用 GCJ-02 坐标、平顶六边形，原点为经度 118.6、纬度 31.85，中心至顶点 570 米。设轴向编号为 `q、r`，中心平面坐标按以下关系排列：

```text
R = 570 米
x = 1.5 × R × q
y = √3 × R × (r + q / 2)
```

再按原点纬度对应的经度比例和每纬度约 111320 米换回经纬度；六个顶点按每隔 60° 生成。每格保存稳定编号、中心和边界，前后端共同使用这份几何。该局部距离换算用于南京旅游范围内的网格制作。

**570 米是六边形几何半径，600 米是普通餐饮查询半径。** 普通餐饮以各格中心为采样点搜索一个圆；鸭店按实际位置归入对应六边形。两者的统计范围需要分别理解。

## 5. 普通“餐饮分布”的采集与绘制

普通餐饮主要于 2026 年 10 月 4 日采集。对每个采样中心调用高德 Web 服务的周边搜索 `/v5/place/around`，参数如下：

| 参数 | 使用方式 |
|---|---|
| `types` | `050000`，餐饮服务类别 |
| `keywords` | 通过餐饮类别检索，关键词留空 |
| `location`、`radius` | 蜂巢中心坐标、600 米 |
| `region`、`city_limit` | 南京 `320100`、限定城市 |
| `sortrule` | 按距离返回 |
| `page_size`、页数 | 每页 25 条，最多 5 页 |

对返回名单检查坐标、南京范围和距采样点的距离，按 POI ID 去重；过滤明确属于咖啡、茶、糕饼、甜品、冷饮、饮品、奶茶等类别的记录，形成该采样圆的用餐类餐饮样本。

正式快照共保存 15819 家去重后的普通餐馆。相邻采样圆会重叠，同一餐馆可出现在多个格子的成员名单中，461 格累计有 17639 个成员关系。每格通过 `ordinary.poi_ids` 引用 `ordinary_shops` 中的门店。

当前快照的分档如下，由 [diningDensityMapLayer.js](../frontend/src/map/diningDensityMapLayer.js) 用高德 `Polygon` 绘制：

| 该中心 600 米圆内的有效样本数 | 显示 | 格数 |
|---|---|---|
| 小于 15 | 隐藏 | 224 |
| 15～48 | 蓝色 | 82 |
| 50～99 | 黄色 | 75 |
| 100 及以上 | 红色 | 80 |

共显示 237 格。当前资料中没有计数为 49 的格；现行读取规则将 49 视为未定义档位，更新数据时需要一并确认分档规则。达到分页上限的采样保留 `is_capped` 标记。图上数字表示本次检索规则取得的样本数，其解释范围受采样半径和分页限制约束。

## 6. 南京鸭和南京特色菜怎样收集

鸭类采集使用高德地点搜索，先做南京全市关键词检索，再细分达到返回上限的区域。采集的关键词分为五组，表中 `|` 表示同组搜索词的“或”关系。

| 分组 | 关键词 |
|---|---|
| 盐水鸭 | `盐水鸭` |
| 鸭血粉丝汤 | `鸭血粉丝汤|鸭血粉丝` |
| 烤鸭 | `金陵烤鸭|南京烤鸭|烤鸭` |
| 板鸭 | `板鸭|南京板鸭|金陵板鸭` |
| 南京特色菜 | `南京特色菜|南京菜馆|金陵菜馆|南京大牌档` |

采集流程：

1. 使用 `/v5/place/text`，餐饮类型 `050000`、南京地区 `320100`，每页 25 条、每组最多 8 页。
2. 查询达到上限时，通过 `/v3/config/district` 取得行政区信息，按区继续关键词检索。
3. 区级查询仍饱和时，利用行政边界的包围范围建立矩形，调用 `/v5/place/polygon`；达到上限的矩形继续四分细化。
4. 合并结果，以 POI ID 去重，结合名称、餐饮类别、业务标签、菜品标签和营业时间分类。对有歧义的门店进行人工复核，再形成正式快照。

采集与筛选保留“正餐候选、外带、其他用餐时段”等服务方式，以及判断理由和证据来源。2026 年 10 月 5 日的人工复核处理了 49 家待定门店，结果为 31 家正餐候选、10 家外带、8 家剔除。

正式 `shops` 共 1670 条互斥记录：1505 家归入南京鸭门店集合，165 家归入南京特色菜集合。南京鸭集合包含 1083 家正餐候选、420 家外带、2 家其他时段门店；南京菜馆标签表达菜系属性，鸭类证据由各门店的独立字段记录。一次关键词命中经过分类与证据整理后才进入相应集合。

同一家鸭店可以有多种鸭类标签，所以盐水鸭、鸭血粉丝汤、烤鸭、板鸭的分类计数允许重叠。正餐候选表示根据已采集资料判断适合安排用餐，具体营业、堂食和菜品情况应结合门店最新信息。

## 7. “南京鸭分布”与“南京鸭”怎样绘制

**南京鸭分布**使用六边形内按 POI ID 去重的鸭店数。门店根据局部坐标和轴向网格计算归格，写入 `display_hex_id`，格子通过 `duck.poi_ids` 引用门店。当前 910 家落在固定 461 格范围内，595 家在范围外仍保留点位；有鸭店的格子共 178 个。

| 六边形内鸭店数 | 分布等级 | 格数 |
|---|---|---|
| 0 | 隐藏 | 283 |
| 1 | 一家 | 61 |
| 2～5 | 中等 | 71 |
| 超过 5 | 较多 | 46 |

[duckDensityMapLayer.js](../frontend/src/map/duckDensityMapLayer.js) 使用高德 `Polygon` 管理蜂巢边界与点击区域，在 Canvas 上绘制不同密度的深棕色条纹，再通过 `AMap.CustomLayer` 叠加到地图。分布统计包括外带店，用户筛选门店时保持该统计口径。

**南京鸭**是门店点图层。[duckRestaurantMapLayer.js](../frontend/src/map/duckRestaurantMapLayer.js) 按坐标绘制门店标记，支持鸭类和外带筛选，并按当前视野筛选要绘制的点位；放大后可显示店名。南京特色菜馆作为独立集合显示。点击蜂巢或门店后，通过快照索引取得名单和详情。

普通餐饮数统计 600 米采样圆，鸭分布数统计实际六边形，而且采集分页和检索条件不同。解释专题图时应分别介绍两种数量，直接计算“鸭店占全部餐馆的比例”会混合两套口径。

## 8. 餐饮数据怎样参与行程

前端 [diningSnapshotData.js](../frontend/src/map/diningSnapshotData.js) 加载快照并建立蜂巢、普通门店和专题门店索引；后端 [route_meals.py](../backend/app/planning/route_meals.py) 读取同一份 JSON 作为用餐区域目录。

规划先预留每餐 60 分钟，再结合实际路径筛选沿途蜂巢。普通餐次使用普通餐饮采样信息，鸭子方案优先选择有鸭类正餐候选的区域，并优先把鸭餐分配到不同日期。公交路径只在可实际到达的步行段、站点等位置匹配候选。最终推荐的是一个可自行选择餐馆的区域，区域与餐次随方案一起保存。

路线用餐区由 [diningMapLayers.js](../frontend/src/map/diningMapLayers.js) 绘制，普通餐馆与鸭店名单从快照取得；用户主动查询附近饭店时，另调用在线餐饮搜索服务。

## 9. 维护数据时需要留意的关系

- 景点 `id` 与图片 `attraction_id`、前端图标和方案节点保持对应；坐标统一为 GCJ-02，经纬度顺序为“经度、纬度”。
- 餐饮快照的 `cells`、`shops`、`ordinary_shops` 通过格子编号和 POI ID 关联；`summary` 应与明细一致。
- 餐饮版本为 `dining-map-snapshot-2026-10-05-v2`，`collection_period` 保存采集时段，`source_digest` 保存来源内容摘要。前端读取器还检查版本、几何和数量等约束，更新快照时需要同步核对这些约束。
- 文化、景点、照片和地铁文件分别保留自己的出处；引用资料和第三方图片的权利归相应作者或服务商，使用时应查看原始来源与授权要求。
